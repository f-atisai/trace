# TRACE Phase 7 — Lifecycle Behavior

**Phase:** 7 — Define Lifecycle Behavior  
**Status:** Draft normative lifecycle specification  
**Scope:** Program START/END events, context-manager behavior, duration, failure handling, and compatibility with simple construction

## 1. Purpose

Every statistical program has an execution lifecycle.

Conceptually:

```text
PROGRAM START
    ↓
READ
    ↓
TRANSFORMATIONS
    ↓
ANALYSIS
    ↓
OUTPUT
    ↓
PROGRAM END
```

TRACE should represent this lifecycle explicitly.

The preferred lifecycle API is optional:

```python
with Trace("T14_01") as trace:
    ...
```

This should generate automatic START and END events.

The existing simple construction must continue to work:

```python
trace = Trace("T14_01")
```

> **Lifecycle automation should add execution boundaries without making context-manager usage mandatory.**

---

# 2. Lifecycle Operations

TRACE reserves two lifecycle operations:

```text
START
END
```

These are not ordinary Tier 1 user operations.

They are system/lifecycle events generated by TRACE.

Typical output:

```text
INFO [START] [T14_01] execution started
...
INFO [END] [T14_01] execution completed – 00:00:08.24
```

If execution fails:

```text
ERROR [END] [T14_01] execution failed – ValueError
```

---

# 3. Context-Manager API

Canonical lifecycle usage:

```python
from trace_tlf import Trace

with Trace("T14_01") as trace:
    ...
```

The object returned by `__enter__()` should be the same usable `Trace` instance.

Inside the block:

```python
with Trace("T14_01") as trace:
    trace.read("ADSL", rows=754, columns=16)
    trace.filter(
        "ADSL",
        "SAFFL == 'Y'",
        before=754,
        after=720,
    )
```

No separate lifecycle object should be required.

---

# 4. START Behavior

Entering the context should emit one START event.

Conceptually:

```python
with Trace("T14_01") as trace:
    ...
```

emits:

```text
INFO [START] [T14_01] execution started
```

Structured form:

```json
{
  "operation": "START",
  "object": "T14_01",
  "action": "execution started",
  "status": null,
  "context": {
    "program": "T14_01"
  }
}
```

A start timestamp should be captured internally for duration calculation.

Exact timestamp representation is deferred to event-envelope hardening.

---

# 5. Successful END Behavior

On normal context exit:

```python
with Trace("T14_01") as trace:
    ...
```

TRACE should emit:

```text
INFO [END] [T14_01] execution completed – 00:00:08.24
```

Structured form:

```json
{
  "operation": "END",
  "object": "T14_01",
  "action": "execution completed",
  "status": "SUCCESS",
  "metrics": {
    "duration_seconds": 8.24
  }
}
```

The exact human-readable duration grammar is a renderer concern.

The structured event should store numeric duration.

---

# 6. Failed END Behavior

If an unhandled exception leaves the context:

```python
with Trace("T14_01") as trace:
    risky_operation()
```

TRACE should emit one failure END event:

```text
ERROR [END] [T14_01] execution failed – ValueError
```

Structured form:

```json
{
  "operation": "END",
  "object": "T14_01",
  "action": "execution failed",
  "status": "FAIL",
  "metrics": {
    "duration_seconds": 2.14
  },
  "details": {
    "exception_type": "ValueError"
  }
}
```

The exception must then propagate normally.

---

# 7. Re-Raise Rule

TRACE must not swallow unhandled exceptions by default.

Context-manager behavior should be equivalent to:

```text
record failure
    ↓
close lifecycle cleanly
    ↓
re-raise original exception
```

This is essential in:

```text
batch execution
CI
workflow orchestration
scheduler environments
QC pipelines
production clinical programming
```

A failed program must still fail visibly to the calling environment.

---

# 8. No Automatic Recovery

TRACE should not:

```text
retry failed operations
convert failures into success
silently continue execution
change exception types
```

Lifecycle logging is observational.

It does not become control flow.

---

# 9. Exception Details

The failure END event should capture safe exception metadata.

Recommended initial fields:

```text
exception_type
exception_message
```

Potential future fields:

```text
exception_module
traceback
failing_step
```

However, traceback capture and rendering should be designed carefully because it can be verbose and may reveal sensitive paths or values.

Phase 7 only requires exception type and optionally message.

---

# 10. Exception Message Privacy

Exception messages can sometimes contain:

```text
file paths
subject identifiers
data values
SQL fragments
credentials
URLs
```

Therefore TRACE should not assume exception messages are always safe for every sink.

Recommended design:

```text
exception_type = safe default
exception_message = available but governed by output/privacy policy
```

Exact redaction policy is deferred.

---

# 11. Duration

Lifecycle should measure elapsed runtime automatically.

Recommended structured metric:

```text
duration_seconds
```

Example:

```json
{
  "duration_seconds": 8.24
}
```

The text renderer may display:

```text
00:00:08.24
```

or another canonical human-readable representation.

Store numeric duration, render formatted duration.

---

# 12. Monotonic Timing

Elapsed duration should use a monotonic clock internally.

This avoids duration errors if wall-clock time changes during execution.

Wall-clock timestamps and elapsed duration are separate concepts.

Conceptually:

```text
wall clock → event timestamp
monotonic clock → duration
```

---

# 13. Simple Construction Remains Valid

This must continue to work:

```python
trace = Trace("T14_01")

trace.read("ADSL", rows=754, columns=16)
trace.output("T14_01", "T14_01.xlsx")
```

No automatic START/END should be assumed merely because an instance exists.

Otherwise lifecycle boundaries become ambiguous:

```text
When did execution begin?
When should END be emitted?
At garbage collection?
At interpreter shutdown?
```

Therefore simple construction means:

```text
manual event logging
no automatic lifecycle boundary
```

unless a future explicit lifecycle method is called.

---

# 14. Why Not Emit START in `__init__()`?

Avoid:

```python
trace = Trace("T14_01")
```

automatically emitting START.

Reasons:

- construction may occur long before execution;
- tests may instantiate TRACE without running a program;
- multiple instances may be prepared in advance;
- there is no reliable automatic END point;
- garbage collection is not a valid lifecycle boundary.

START should correspond to an explicit lifecycle action.

The context manager provides that action naturally.

---

# 15. Why Not Emit END in `__del__()`?

Do not use object destruction for lifecycle completion.

`__del__()` is unreliable for:

```text
timing
process termination
reference cycles
interpreter shutdown
exceptions
deterministic ordering
```

Clinical execution logs require deterministic behavior.

---

# 16. Optional Explicit Lifecycle Methods

A future explicit API may support:

```python
trace.start()
...
trace.end()
```

This could be useful where context managers are inconvenient.

However, Phase 7 does not require these methods.

If added, they must use the same lifecycle state machine as the context manager.

The preferred lifecycle API remains:

```python
with Trace(...) as trace:
    ...
```

---

# 17. Lifecycle State

A `Trace` instance that participates in automatic lifecycle should conceptually track:

```text
NOT_STARTED
RUNNING
ENDED
```

This can prevent invalid behavior such as:

```text
double START
double END
END before START
```

Exact state enum design is implementation detail.

---

# 18. Double Entry

This should not silently emit duplicate START events:

```python
trace = Trace("T14_01")

with trace:
    with trace:
        ...
```

Recommended initial behavior: reject nested entry of the same `Trace` instance.

A clear lifecycle error is preferable to ambiguous nested program boundaries.

Nested *steps* may be supported later through a separate step API.

---

# 19. Reusing an Ended Trace Instance

Consider:

```python
trace = Trace("T14_01")

with trace:
    ...

with trace:
    ...
```

Recommended v0.x behavior:

```text
do not permit automatic lifecycle reuse of the same instance
```

Create a new instance for a new program run:

```python
with Trace("T14_01") as trace:
    ...
```

This avoids ambiguity around:

```text
run identity
handler state
duration
event sequence
file mode
context
```

Reuse could be reconsidered later if a formal reset/run API exists.

---

# 20. START/END Object

Lifecycle events should use the configured program identifier as their primary object.

Example:

```python
Trace("T14_01")
```

produces:

```text
[START] [T14_01]
[END]   [T14_01]
```

This keeps lifecycle logs immediately recognizable in batch output.

---

# 21. Lifecycle and Context

START and END should inherit the same configured context as all other events.

Example:

```python
with Trace(
    "T14_01",
    study="ABC123",
) as trace:
    ...
```

Both lifecycle events inherit:

```json
{
  "program": "T14_01",
  "study": "ABC123"
}
```

---

# 22. Run Identity

Lifecycle introduces a strong need for a run identifier.

A future event envelope should likely include:

```text
run_id
```

generated when automatic lifecycle starts.

That would allow all events from one execution to be correlated reliably.

Example concept:

```json
{
  "context": {
    "program": "T14_01",
    "study": "ABC123",
    "run_id": "..."
  }
}
```

Phase 7 recommendation:

> A `run_id` should be generated automatically for context-managed runs.

Exact format is deferred.

---

# 23. Run ID and Simple Construction

For simple construction:

```python
trace = Trace("T14_01")
```

there are two reasonable options:

1. generate `run_id` at construction;
2. omit `run_id` unless lifecycle begins.

Recommendation:

```text
generate run_id at Trace instance creation
```

because all events from that instance then share a stable execution identity even without the context manager.

The context manager defines lifecycle boundaries; the instance defines run identity.

---

# 24. Lifecycle Status

Recommended mapping:

```text
START
    status = None

successful END
    status = SUCCESS

failed END
    status = FAIL
```

This follows the Phase 0 separation of:

```text
operation
status
severity
```

---

# 25. Lifecycle Severity

Recommended defaults:

```text
START success boundary → INFO
END success            → INFO
END failure            → ERROR
```

This is one of the first severity mappings that can be safely frozen because lifecycle outcome is unambiguous.

Broader severity inference for all operations remains a separate design concern.

---

# 26. KeyboardInterrupt and SystemExit

The context manager should treat exceptions derived from `BaseException` carefully.

For events such as:

```text
KeyboardInterrupt
SystemExit
```

TRACE should not swallow them.

A reasonable lifecycle policy is:

```text
emit failed/interrupted END if safe
re-raise immediately
```

Exact status terminology may later distinguish:

```text
FAIL
INTERRUPTED
```

Since `INTERRUPTED` is not currently part of the Phase 0 status vocabulary, Phase 7 should use FAIL unless the status model is extended deliberately.

---

# 27. END Event on Logging Failure

TRACE should avoid masking the original program exception if logging the failure event itself encounters an internal problem.

Priority should be:

```text
original program exception
    >
TRACE lifecycle logging exception
```

In other words, instrumentation must not obscure the root failure.

Exact fallback behavior belongs to implementation/error handling.

---

# 28. Lifecycle and File Logging

The lifecycle design informs the deferred file-mode question from Phase 6.

Because one `Trace` instance represents one run identity, file behavior should eventually be defined relative to runs rather than object destruction.

Possible future choices:

```text
append each run to program log
one log file per run
explicit overwrite
```

Phase 7 does not freeze file mode yet.

It does establish the lifecycle information needed to make that decision correctly.

---

# 29. Example — Successful TLF Program

```python
from trace_tlf import Trace

with Trace(
    "T14_01",
    study="ABC123",
    log_file="logs/T14_01.log",
) as trace:

    adsl = pd.read_csv("adsl.csv")
    trace.read(
        "ADSL",
        source="adsl.csv",
        rows=len(adsl),
        columns=len(adsl.columns),
    )

    safety = adsl.loc[adsl["SAFFL"] == "Y"].copy()
    trace.filter(
        "ADSL",
        "SAFFL == 'Y'",
        before=len(adsl),
        after=len(safety),
    )

    summary = (
        safety.groupby(["TRT01A", "SEX"])
        .size()
        .reset_index(name="N")
    )
    trace.aggregate(
        "ADSL",
        by=["TRT01A", "SEX"],
        result="summary",
    )

    summary.to_excel("T14_01.xlsx")
    trace.output(
        "T14_01",
        "T14_01.xlsx",
        rows=len(summary),
    )
```

Possible output:

```text
INFO [START]     [T14_01] execution started
INFO [READ]      [ADSL] loaded – N=754, Vars=16
INFO [FILTER]    [ADSL] SAFFL == 'Y' applied – N=754 → 720
INFO [AGGREGATE] [ADSL] summarized – by=TRT01A,SEX, result=summary
INFO [OUTPUT]    [T14_01] written – T14_01.xlsx
INFO [END]       [T14_01] execution completed – 00:00:08.24
```

# 30. Example — Failed Program

```python
with Trace("T14_01") as trace:
    adsl = pd.read_csv("adsl.csv")
    trace.read(
        "ADSL",
        rows=len(adsl),
        columns=len(adsl.columns),
    )

    raise ValueError("Expected treatment variable missing")
```

Possible output:

```text
INFO  [START] [T14_01] execution started
INFO  [READ]  [ADSL] loaded – N=754, Vars=16
ERROR [END]   [T14_01] execution failed – ValueError
```

The original `ValueError` then propagates.

---

# 31. Example — Simple Non-Context Usage

```python
trace = Trace("T14_01")

trace.read(
    "ADSL",
    rows=754,
    columns=16,
)

trace.output(
    "T14_01",
    "T14_01.xlsx",
)
```

Output contains only explicitly logged operations.

No implicit START/END is generated.

---

# 32. Lifecycle Is Not a Step System

Program lifecycle and nested execution steps are different concepts.

Program lifecycle:

```text
START
...
END
```

Future step API:

```text
step start
...
step end
```

Do not overload START/END semantics prematurely.

A later phase may define:

```python
with trace.step("Analysis population"):
    ...
```

but that should build on, not replace, program lifecycle.

---

# 33. Lifecycle and Generic Logging

Users should not normally write:

```python
trace.log(
    "START",
    object="T14_01",
    action="execution started",
)
```

or:

```python
trace.log(
    "END",
    object="T14_01",
    action="execution completed",
)
```

Lifecycle events should be system-generated whenever lifecycle automation is active.

This prevents duplicated or inconsistent boundaries.

---

# 34. Lifecycle and Tier 1 API

Lifecycle does not change the Tier 1 operation signatures.

This remains valid:

```python
trace.filter(
    "ADSL",
    "SAFFL == 'Y'",
    before=754,
    after=720,
)
```

The only difference is inherited lifecycle context and automatic boundary events.

---

# 35. Proposed Internal Context-Manager Contract

Conceptually:

```python
def __enter__(self):
    ensure_not_started()
    mark_running()
    capture_start_time()
    emit_start_event()
    return self

def __exit__(self, exc_type, exc, tb):
    duration = elapsed()

    if exc_type is None:
        emit_success_end(duration)
    else:
        emit_failed_end(
            duration=duration,
            exception_type=exc_type.__name__,
        )

    mark_ended()

    return False
```

Returning `False` ensures exceptions propagate.

This is conceptual behavior, not implementation code to freeze line-for-line.

---

# 36. Phase 7 Decisions

**P7-01** — TRACE recognizes automatic program lifecycle through `START` and `END` events.

**P7-02** — The preferred automatic lifecycle API is:

```python
with Trace("T14_01") as trace:
    ...
```

**P7-03** — Context-manager usage is optional.

**P7-04** — `Trace("T14_01")` without a context manager remains valid and does not automatically emit START/END.

**P7-05** — Context entry emits one INFO START event.

**P7-06** — Normal context exit emits one INFO END event with `SUCCESS`.

**P7-07** — Exceptional context exit emits one ERROR END event with `FAIL`.

**P7-08** — Unhandled exceptions are re-raised; TRACE does not suppress them.

**P7-09** — Duration is measured automatically and stored numerically as `duration_seconds`.

**P7-10** — Duration measurement should use a monotonic clock.

**P7-11** — Lifecycle events inherit normal TRACE context.

**P7-12** — Lifecycle events use the program identifier as their semantic object.

**P7-13** — A stable `run_id` should exist for all events from a Trace instance.

**P7-14** — Nested context entry of the same Trace instance should be rejected.

**P7-15** — Reusing an ended Trace instance for a second automatic run should be rejected initially.

**P7-16** — START/END should normally be generated by lifecycle machinery, not manually through `trace.log()`.

**P7-17** — Explicit `trace.start()` / `trace.end()` methods may be considered later but are not required for v0.x lifecycle design.

---

# 37. Acceptance Criteria

Phase 7 is complete when:

1. program lifecycle has explicit START and END semantics;
2. context-manager use automatically records lifecycle boundaries;
3. successful runs record completion and duration;
4. failed runs record failure and exception type;
5. original exceptions propagate unchanged;
6. simple non-context-manager construction still works;
7. no lifecycle relies on garbage collection or interpreter shutdown;
8. lifecycle state prevents duplicate/nonsensical boundaries;
9. run identity can correlate all events from one Trace instance;
10. lifecycle behavior remains backend-independent and observational.

---

# 38. Outcome

TRACE now supports two valid execution styles.

## Explicit event logging only

```python
trace = Trace("T14_01")
```

## Automatic lifecycle

```python
with Trace("T14_01") as trace:
    ...
```

The lifecycle form produces:

```text
INFO [START] [T14_01] execution started
...
INFO [END] [T14_01] execution completed – 00:00:08.24
```

or on failure:

```text
ERROR [END] [T14_01] execution failed – ValueError
```

> **TRACE should make the execution boundary visible while leaving program control flow unchanged.**
